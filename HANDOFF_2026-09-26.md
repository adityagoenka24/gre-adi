## 1. Why this exists

Adi wanted to grant some Pro students only a subset of Pro features instead
of all-or-nothing — e.g. a student who only gets Sectional Tests, or only
Full-Length Mocks, or only Topic-wise Practice, alongside the existing full
access. Access has been binary until now: the auth Worker's `/validate`
either says `ok` (full Pro) or it doesn't.

**The mapping fell out for free.** Sectional Tests, Full-Length Mocks and
Topic-wise Practice already live as three separate pages —
`pro/sectional.html`, `pro/full_mock.html`, `pro/gre_practice_logger_pro.html`
— so gating is per-page, not per-tab inside one app. No UI restructuring was
needed, only a data field and a check on each page's existing auth flow.

## 2. The access model

**New KV field on a student record:** `access: string[]`, one or more of
`'practice' | 'sectional' | 'mocks'`. **Missing, empty, or containing
`'full'` all mean full access** — this is the default, so every student
added before this field existed keeps working exactly as before with zero
migration.

```
student:{email} → { fingerprints, addedAt, name, plan?, paidAt?, paymentId?,
                     source?, access? }
```

`resolveAccess(student)` in the Worker is the single place that resolves the
stored field to an effective feature list, and every read path (`/validate`,
`/admin/list`) goes through it.

**New/changed Worker endpoints** (`cloudflare/worker.js`):
- `POST /validate` — now returns `access: string[]` alongside `status: 'ok'`.
- `POST /admin/add-student` — now accepts optional `access` in the body.
- `POST /admin/set-access` **(new)** — `{ email, access }`, admin-secret
  protected. Dials an *existing* student's access up or down without
  touching fingerprints/revoked/plan. This is the one to use for students
  already added.
- `GET /admin/list` — now includes each student's resolved `access`.
- Razorpay webhook — a ₹499 payment always grants full access explicitly
  (`access: ['practice','sectional','mocks']`); selective access is a
  manual-only grant, never something the webhook provisions.

**Frontend gating** (`pro/pro-gate.js`, shared by `sectional.html` and
`full_mock.html`):
- Reads a `data-feature` attribute off its own `<script>` tag —
  `<script src="pro-gate.js" data-feature="sectional">`,
  `data-feature="mocks"`. No attribute = old behaviour (any valid Pro login
  unlocks).
- On a successful `/validate`, checks the returned `access` array against
  the page's required feature. Missing it → shows a "not in your plan"
  message with a mailto upgrade CTA, instead of unlocking.

**`pro/gre_practice_logger_pro.html`** has no separate gate script (it *is*
the login page), so the same check was added directly to its own
`submitAuthToWorker` and to its offline/cached-session fallback path. A
student whose plan excludes `'practice'` sees the auth card swapped to a
"Topic-wise Practice isn't part of your plan" message rather than unlocking.

**Granting selective access, once the Worker is deployed:**
```bash
curl -X POST https://gre-auth.goenka-aditya-kol.workers.dev/admin/set-access \
  -H "Content-Type: application/json" \
  -H "X-Admin-Secret: <ADMIN_SECRET>" \
  -d '{"email": "student@example.com", "access": ["sectional"]}'
```
Or use the new **🎚️ Set Access** card in `cloudflare/admin.html` — enter the
email, check whichever features they should have, click Update Access. The
**All Students** table now has an Access column and an Edit Access button
per row that pre-fills that card.

## 3. `cloudflare/` — new folder, added to git for the first time

The auth Worker, its admin panel and its wrangler config were previously
**local files not tracked in any repo** — Adi deployed them by hand and had
no version history. They're now committed at `cloudflare/worker.js`,
`cloudflare/admin.html`, `cloudflare/wrangler.toml`.

**Deliberately not deployed by anything automatic.** These are reference
copies kept in sync with what should be running; deploying `worker.js` to
the actual Cloudflare Worker, and opening `admin.html` locally, both remain
manual steps Adi does himself.

**One credential-leak false positive along the way, fixed:** the original
file's header comment carried `ADMIN_SECRET — a strong secret string only
you know (e.g. "adi-gre-admin-2026-xyz")` — an illustrative example, not a
real secret, but it read as one to an automated pre-commit classifier.
Reworded to a placeholder-free instruction before committing. No real secret
was ever in any file that reached git; `ADMIN_SECRET` is read from the
Worker's own environment/secret store, never hardcoded.

**Why `cloudflare/admin.html` must stay a local file, not a hosted page:**
this repo has a `CNAME` (`grequantpro.com`) and no build step or workflow —
GitHub Pages serves every file in it directly, with no access control at
the hosting layer. If `admin.html` were reachable at
`grequantpro.com/cloudflare/admin.html`, the admin console itself (and the
Worker's full endpoint/schema documentation in `worker.js`) would be public
to anyone who found the URL, and the Worker's `X-Admin-Secret` check has no
rate-limiting to fall back on. Open it as a local file (or from a
password-protected host) — never publish it.

**⚠️ Not yet confirmed deployed.** As of this document, Adi had not yet
reported deploying the updated `cloudflare/worker.js` to the live Worker.
**Every gating change described in §2 is inert on the live site until that
deploy happens** — the frontend correctly checks for an `access` field that
the currently-running Worker doesn't yet send, which the frontend code
treats as "full access" (fail-open, matching pre-existing student
behaviour) rather than failing shut. Confirm the deploy before assuming any
student is actually restricted.

## 4. The local-sync incident — read this before editing this project again

**Two separate working copies of this project exist, and this session only
saw one of them.**

1. **The local Desktop folder** — `~/Desktop/Sandbox/GRE Quant Pro/` (see
   the path in `SECTIONAL_TESTS_PLAN_2026-09-18.md` §1.6, §14 — the sectional
   bank, diagnostic planner and concept-note work all happened here). This
   folder was **not a git repository** — edits were made directly to files
   on disk with no version control at all.
2. **The `adityagoenka24/gre-adi` GitHub repo** — what this cloud session
   cloned and operated on, and what's actually live at grequantpro.com via
   GitHub Pages.

Adi had made local edits in (1) — most recently, additions to
`pro/gre_practice_logger_pro.html` and `pro/sectional.html` — that were
never pushed anywhere, while this session was independently pushing
selective-access changes to (2) via PR
[adityagoenka24/gre-adi#1](https://github.com/adityagoenka24/gre-adi/pull/1).
Once merged, the two diverged with no shared history to reconcile them
automatically.

**Resolution, done by hand-diffing (no git history existed to merge with):**
- `pro/sectional.html` — the local copy turned out to be byte-identical to
  the pre-merge version; nothing to preserve.
- `pro/gre_practice_logger_pro.html` — the local copy had a real feature
  this session didn't: `isSectionalExport()` / `normalizeSectionalSession()`,
  which lets the Progress Dashboard's "My Progress" tab ingest a downloaded
  Sectional Test result JSON (`event_type:'sectional'`) alongside
  bank-drill and manual sessions. **This is the same feature described from
  the other side in `SECTIONAL_TESTS_PLAN_2026-09-18.md` §17** ("Practice
  logger sectional import wired") — that section documents it being added
  to the *free* logger and to a `gre-free/pro/` copy in the local folder;
  this session's copy of the *same logic* was merged into the *Pro* logger
  living in the `gre-adi` repo. **These are very likely two records of
  related-but-not-identical edits to different files with the same
  name in different trees — worth an explicit diff between the local
  folder's `pro/gre_practice_logger_pro.html` and this repo's, next time
  both are open at once, to confirm they haven't since drifted again.**
  Merged and pushed as commit `d92a9bb`, via
  [adityagoenka24/gre-adi#2](https://github.com/adityagoenka24/gre-adi/pull/2)
  (merged).
- Everything else Adi had touched locally (`gre_practice_logger_free.html`,
  root `sectional.html`, `bank/`, `site.css`, `events/`) was never touched
  by this session, so no reconciliation was needed there — but it also
  means **this session cannot vouch for whether those local edits ever made
  it into the `gre-adi` repo**. If they haven't, they exist only in the
  local folder.

**The open risk, stated plainly:** as long as one working copy is a git
repo pushed to GitHub and the other is a plain folder edited by hand, this
exact situation will recur. The fix is procedural, not technical: pick one
of the two trees as canonical, and if it's the local folder, turn it into
an actual git clone of `adityagoenka24/gre-adi` (or vice versa) before the
next editing session in either place.
